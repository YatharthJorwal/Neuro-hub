# decisions.md

Short log of choices made and why, so they don't get re-litigated
without an actual reason to. Newest entries at the bottom.

## Tauri over Electron
The memory backend needed to be Rust either way (SQLite + the ranking
logic). Tauri's backend *is* Rust, so the memory crate drops in with
zero glue. Electron's backend is Node — the alternative would've meant
rewriting the store in JS, or running the Rust code as a separate
sidecar process talking over stdio. More moving parts for no benefit.

## Skip InnerCortex.zip / "Project Neuro" as the starting point
It's the same visualization as the plain `index.html` in the Neuro-hub
repo — confirmed by diffing them, the differences were cosmetic
refactoring only. The zip wraps that same code in a much bigger
React/Vite/TanStack Start scaffold generated by Grok's App Builder,
including auth and a Postgres schema that have nothing to do with the
visualization itself. Not worth untangling. Built from the plain
`index.html` instead.

## No vector database for memory
At personal-app scale (hundreds to low thousands of remembered facts),
brute-force cosine similarity computed in Rust over every row is simpler
to get right than standing up `sqlite-vec` or an external vector store,
and plenty fast at that scale. Revisit only if the fact count actually
grows large enough for it to matter.

## Placeholder (mock) embedder, on purpose
Shipped the memory system with a deterministic, non-semantic hash as the
embedder specifically to prove the storage/ranking pipeline end to end
without taking on a model download mid-build. Demonstrated live that
`recall_facts` ranks meaninglessly with it — a query for "what GPU does
the user have" ranked an unrelated "favorite color" fact above the
actual hardware fact. Swapping in a real embedder is a known, explicit,
not-yet-done next step (see plans.md), not an oversight.

## DB in the OS app-data directory, not next to the executable
A relative path breaks once the app is packaged and run from Program
Files or similar. Used Tauri's `app.path().app_data_dir()` instead, so
the database survives packaging and app updates.

## Embedder: local, not API
Chosen over an API embeddings call specifically for privacy — this is a
local-first "digital brain" app, and calling out to a cloud API just to
remember a fact runs against that. Runs fine on the RTX 3060, or even
CPU given how small and infrequent the calls are. Not yet implemented —
`memory.rs` still has the placeholder hash embedder (see above). Likely
candidate: fastembed-rs with a small model (e.g. BGE-small).

## Chat layer: local LLM, not Claude API
Same reasoning as the embedder — fully private, everything stays on the
user's machine. Not started. Worth flagging early: a local LLM, a local
embedder, and the Three.js visualization will all be competing for the
3060's 12GB of VRAM at the same time. The embedder is small enough this
probably isn't a real constraint, but the LLM's size will need picking
with that budget in mind rather than assumed away. No model has been
chosen yet.

## Force-pushed the app over the old repo contents
The repo previously held only the standalone `index.html` demo, which
shares no git history with the new app's file tree, so force-push was
the only way to replace it. Whether the old file was preserved somewhere
(e.g. moved to `legacy/`) first wasn't confirmed in the session that did
the push — worth checking the repo directly rather than assuming.
